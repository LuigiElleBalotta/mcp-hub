- [x] 1. Spike: feed the SDK `StreamableHTTPServerTransport` to a transport-independent pump; confirm Claude Code connects with `type: http` and a bearer header. Record the result here; choose SDK transport or hand-written handler.
  - Result (read from mcp 2.2.0 source, not yet run): `StreamableHTTPServerTransport.connect()` yields the same `(read, write)` `SessionMessage` streams as `connect_sse`, so `_proxy` runs on it unchanged. The SDK's `StreamableHTTPSessionManager` requires an `mcp.server.Server` to drive, which the hub does not have, so the hub gets its own small session registry that mirrors `_handle_stateful_request` (new session on a request without `Mcp-Session-Id`, route by id, 404 on unknown, discard on DELETE/idle). Decision: use the SDK transport + own registry, no hand-written protocol code.
  - A server message needs `ServerMessageMetadata(related_request_id=...)` to land on the right POST response stream instead of the standalone GET stream (done in task 2).
  - Observation: `apply` today writes `type: "http"` with the `/sse` URL, which works only because Claude Code evidently falls back; once `/mcp` exists the matching pair is `http` + `/mcp` (task 6). Whether Claude Code accepts the bearer header on `http` is checked in task 10 with a real run.

- [x] 4. Lazy start, `ensure_running`, idle watcher, `persistent`, `idle` status
  - `startMode`/`idleTimeout`/`persistent` (MCP only, omitted while default). Status `idle` = not running but starts by itself when asked; a deliberate Stop or a crash is NOT undone by a request. A lazy server answers `initialize` and cached lists from `<data dir>/cache/<name>.json` without spawning (key = command line + env NAMES). Idle shutdown never cuts a request in flight; status flips to `idle` before the process is gone on purpose (a request arriving then waits on the spawn lock, then respawns).
  - Fixed on the way: `handle_sse`/`handle_message` asserted a process exists; `_spawn` now stops the previous process's stdout reader and rejects its pending requests first, so a late EOF cannot reject the new process's requests.
- [x] 5. Session modes: `isolated` pool and `session-aware` `_meta` injection
  - `concurrency` accepts exclusive | parallel | session-aware | isolated (validated on load via API and in the GUI later). session-aware injects `params._meta["io.github.mcp-hub/sessionId"]` into every forwarded request, merged with the client's own `_meta` and the remapped progress token. isolated: the server entry has no process; `ManagedServer.session_upstream()` creates a private lazy child per SSE connection and `release_session_upstream()` stops it on disconnect; children share no cache, handshake or request ids, their logs show on the parent, status shows `running`/`idle` with a `sessions` count. `ManagedServer` is now `eq=False` (identity hash). Proven end to end with two real SDK clients.
- [x] 6. Streamable HTTP endpoint and `preferredTransport` in `apply`
  - `streamable.py`: `StreamableSessions` (own registry around the SDK `StreamableHTTPServerTransport`, pump = `_proxy`), mounted at `/<name>/mcp`; unknown/expired session id -> 404 so the client re-initialises; sessions in memory, idle timeout 30 min, ended when the server entry is replaced or the hub stops. Proven with the real SDK client: tools, two clients with separate progress, SSE + Streamable on one upstream, token/Origin, crash recovery on the same session, isolated mode cleanup.
  - Fixed on the way (pre-existing bug): `build_app` rebuilt every server's `SseServerTransport` on each route rebuild, so ANY upsert/remove/reload of one server left every connected SSE client of every other server without a session and hung it (reproduced first: the new regression test timed out). Transports now live in a per-server registry that survives rebuilds.
  - `apply`: `hub.preferredTransport` "sse" (default, writes exactly what it always wrote) or "http" (`/mcp`). Not yet verified: Claude Code against `/mcp` with a bearer header (task 10).
- [x] 7. Graceful drain, shutdown/self-update integration
  - `POST /api/drain {timeout}` (waits, reports `{drained, inFlight}`; `DELETE /api/drain` resumes), `POST /api/shutdown {drainTimeout}` replies at once and drains + exits in the background (so the GUI's 5 s HTTP timeout is not an issue; `shutdown_hub`'s wait raised 30 -> 60 s to cover the 20 s default `hub.drainTimeout`). While draining `DrainGate` answers every non-`/api/` request with 503 + `Retry-After: 5`, except DELETE. `/api/status` shows `draining: true`. In-flight counting includes isolated children.
  - Known limitation (by design, in the spec): a client's follow-up request on an existing session during the drain also gets 503; the SDK SSE client does not surface that and waits until the hub exits and it reconnects (a few seconds at most). After a restart Streamable clients get 404 and re-initialise.
